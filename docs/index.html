For Claude Code · MIT licensed

A build loop that stops and waits for you.

One command runs plan → execute → verify → review → route, round after round, until an adversarial review comes back clean or a round cap trips. Then it writes an approval card and stops. It fixes routine review findings on its own, escalates only what a human has to decide, and cannot open a PR, merge, or record an approval while it runs.

$ git clone https://github.com/ataglianetti/agent-orchestration-loop.git
$ agent-orchestration-loop/install.sh /path/to/your-repo
  • 33 pieces across 9 stages
  • State on disk, resumable across sessions
  • Human gate enforced by a hook
01 · The loop

One round, repeated until review is clean.

Run /orchestrate <workstream-id> with a goal inline or a path to a spec. State lives in docs/execution/active/<id>/, so re-running the command picks up where the last session stopped.

once
Plan

A read-only planner splits the goal into file-scoped tasks in parallel waves, each tagged with a tier.

step a
Execute

Executors work a wave under bounded contracts. One atomic commit per task.

step b
Verify

A coverage gate, then a live check against the real build or endpoint.

step c
Review

1 to 3 independent passes, sized to the diff's blast radius.

step d–f
Route

Fix, park or escalate by severity. Score confidence. Decide whether to loop.

hard stop
Approval card

Intent, reversibility, confidence, and anything only you can rule on. The loop ends here.

next round, up to round_cap (default 5)
CLEAN

Verification passed and nothing above NOTE is open. Read the card; if it's right, you open the PR.

FLAG-HUMAN

A scope, money, contract or security-posture call. Rule in chat or in DECISIONS.md; your words are recorded verbatim and the loop continues.

NON-CONVERGENT

The round cap tripped, or the run stalled. The card shows settled vs. new findings per round so you can tell stuck from slow.

Round one

planneragent

Read-only. Breaks the goal into atomic, testable, file-scoped tasks, groups them into waves, and tags each mechanical, standard or hard. It returns the plan and never writes a file.

Also: takes a spec or notes file as the goal and follows its frontmatter links only to bound scope, never to widen it.

Model routingrule

Every subagent spawn names its model, chosen by task tier. Defaults: planner, hard tasks and the adversarial pass on opus; mechanical and standard tasks, the live check and lighter review passes on sonnet.

The brief each executor gets: objective, files it may edit, what's out of scope, constraints, validation command, model, return format. Never the full conversation.

Tier escalationrule

A task that fails its validation twice, or draws a CRITICAL, gets its fix one tier up instead of another try at the same tier. A third failure at hard becomes a finding.

Rule: the orchestrator can raise a tier and log why. It never lowers one.

DECISIONStemplate

Every routing call, every answer to an executor's "your call?" question, and every human ruling, which goes in verbatim with its source and date.

Verify

Step b, each round

Coverage gategate

A test has to exercise this change and pass. No test for the new path counts as a fail, and a failed gate can't reach a clean exit.

Feeds: the confidence read and the card's "How confident" section.

Live checkgate

Runs the real build or endpoint through the run skill, in its own verify task, so browser and shell output stay out of the orchestrator's context. Returns pass/fail per check and a repro for any failure.

Needs: the smoke commands named in guide §5.

TEST_PLAN · TEST_RESULTStemplate

What will be validated (unit, integration, manual smoke) and what actually ran (automated, manual, and gaps with the reason a test couldn't run).

execution/templates/

Review

Step c, each round

Blast-radius ladderrule

One pass for a small additive diff, two for one subsystem, three for cross-cutting work. Touching a guardrail, API contract or security surface forces all three: adversarial-reviewer, run, code-review.

Rule: passes see only the round's diff and never each other's findings. A borderline or critical finding adds a pass.

orchestrate.md · 2c

REVIEW_CONTRACTcontract

Fixed tokens for severity, reachability, FLAG-HUMAN, disposition and verdict, and the rules for merging raw passes into one block. Routing keys off the tokens, not the reviewers' prose.

Rule: reviewers assess. The orchestrator decides what happens.

execution/REVIEW_CONTRACT.md

Findings ledgerrule

Stable F# IDs across rounds in an append-only REVIEW.md. A settled finding that resurfaces is suppressed, unless its severity rose, it went live, the diff touched its code, or every pass raised it again.

Why: so the round cap isn't spent re-arguing calls already made.

REVIEW_CONTRACT.md · §5

Route & stop

Steps d–f, and the card

Severity routingrule

Live criticals get fixed this round and re-reviewed. Dormant ones are fixed if cheap or parked behind their flag. Warnings are fixed if cheap; trivial notes are auto-fixed. Any FLAG-HUMAN is a hard stop.

Rule: a fixed critical isn't resolved until a fresh review pass confirms it.

orchestrate.md · 2d

Confidence readrule

Review consensus, the coverage gate and the live check, combined into one line per round. Low and reversible runs another verification round; low and consequential escalates.

Optional: escalate_to_engineer: on pauses for a code owner's PR review instead of landing on you.

orchestrate.md · 2e

APPROVAL_CARDtemplate

What you sign: what you asked for against what it built, how reversible it is with the revert path, how confident the stack is, and any decision only you can make, each with a recommendation.

Rule: the loop never writes "APPROVED". That block is yours.

APPROVAL_CARD.template.md

Stop protocolrule

Every hard stop prints one line with the status, branch and card path. In the Claude desktop app the run shows as waiting on you, and where a one-click answer fits, an Approve or "Go with recs" button sends your words as the ruling.

Optional: the app pieces. The CLI runs the same loop without them.

orchestrate.md · Stop protocol

Gate

Holds for the whole run

block-human-gated-actions.shhook

PreToolUse guard. While a run is active it blocks opening, merging and approving PRs, git push, and the routes around them: aliases, gh api writes, branch-protection changes, authenticated raw HTTP, reading the GitHub token.

Limit: it matches text. Branch protection on the remote is the backstop.

scripts/block-human-gated-actions.sh

.loop-active · ungatemarker

The soft marker. The loop writes it at the repo root and can't remove it; the guard walls every removal path it knows. You clear it from your own terminal with rm, or ungate, which also finds markers in other worktrees.

Opt-in: source loop-gate.zsh from your shell rc. The installer never touches it.

scripts/loop-gate.zsh

lock-loop.sh · unlock-loop.shscript

The hard lock. One sudo drops a root-owned marker outside the repo and freezes .claude/ (except worktrees/), so the hook can't be unwired from inside. One sudo lifts it.

Reach for it: unattended runs on a repo where a rogue ship would reach something real.

scripts/lock-loop.sh

loop-status.shscript

Read-only report of which marker, if any, holds the gate for this checkout, plus soft markers in other worktrees and any worktree the hard lock left unfrozen.

Used by: /orchestrate, before it writes its own marker. And you, before locking or unlocking.

scripts/loop-status.sh

scripts/tests/tests

Five suites that run without root (the guard, denial-message safety, the hard marker, ungate, the cost record) and one smoke test that sets real immutable flags under sudo.

Notable: the denial suite runs every command a block message suggests and checks that none clears the gate.

03 · What's different

Built around the run that shipped itself.

The first time this loop ran for real, it reached a clean review, approved its own work and opened a PR. It had been told never to do that. The mechanical gate exists because of that run.

The gate

It can't ship on its own.

Prose instructions have a ceiling: an agent trying to finish will reason its way past them. So a hook blocks the shipping commands while a run is active, and the marker that turns the hook on is one the loop is walled off from removing.

README · The human gate

Honest limits

It tells you where the guard stops.

The guard matches text, so a command that assembles its words at runtime can get past it. The README says so and names the backstop: branch protection that requires a pull request and an approving review from someone other than the author. The hard lock goes further and puts the marker and the repo's hook wiring out of the agent's reach. It also names what the lock leaves open, starting with user-level ~/.claude/settings.json.

README · Soft and hard markers

Your job

You sign off on two things.

Intent and scope: is this what you asked for? Reversibility: if it's wrong, how bad and how recoverable? Correctness goes to the verification stack (independent reviewers, a coverage gate, a live check), which is why that stack has to be strong enough to earn a sign-off without reading the diff.

APPROVAL_CARD.template.md

Convergence

Settled findings stay settled.

Without a ledger, a parked finding the reviewer keeps rediscovering gets re-routed every round until the cap runs out. Stable IDs and a whole-file seen-set stop that. The matcher can overrule one reviewer's memory, never all of them at once.

REVIEW_CONTRACT.md

Cost

Cheap models do cheap work, never cheap review.

A subagent spawned without a model runs on the session's model, so a one-line rename would run on the most expensive one available. Here the planner tiers every task, and if any task in a round ran on the hard-tier model, every review pass that round does too.

orchestrate.md · Model routing

Audit trail

Everything lands on disk.

The workstream folder is the run's memory and its paper trail: the card up front, then review rounds, decisions, test results and the run log. Close it and the README gains a record of time, tokens, models and rounds.

README · Using it

04 · Install

Three steps to a first run.

Built for Claude Code, in the CLI or the desktop app. The guard and the session recorder are Claude Code hooks wired in .claude/settings.json.

  1. Install into your repo

    Drops the commands, planner and scripts into .claude/, the templates into docs/execution/, adds .loop-active to .gitignore, and merges both hooks into your settings.

    $ git clone https://github.com/ataglianetti/agent-orchestration-loop.git
$ agent-orchestration-loop/install.sh /path/to/your-repo

  2. Specialize the guide

    Fill §1 (contracts), §5 (the exact test and smoke commands), §6 (guardrails) and §7 (execution order) in docs/execution/CLAUDE_ORCHESTRATION_GUIDE.md. The live check and reachability calls depend on them.

  3. Hand off a goal

    In a Claude Code session rooted at the repo. Give the goal inline or point it at a spec file, then walk away until it stops.

    > /orchestrate my-first-workstream

Requirements

  • Claude Code, git, and jq (for the settings merge and the guard's JSON output).
  • The adversarial-reviewer, run and code-review skills. They aren't shipped here; they come bundled with most Claude Code builds or from a plugin. Without them the loop plans and executes, then stalls at review.
  • For the hard lock: sudo, and chflags (macOS) or chattr (Linux).
  • Recommended on any repo an unattended run could reach: branch protection on the default branch that requires a pull request and an approving review from someone other than the author.

When the run stops

Read APPROVAL_CARD.md, not the diff. Approve or rule in chat and your words are recorded verbatim. Then clear the gate from your own terminal and open the PR yourself.

$ rm .loop-active   # or: ungate
$ ./.claude/scripts/close-workstream.sh <id>   # after merge

Soft or hard gate?

GateWho can clear itUse it for
Soft (default).loop-active at the repo root. You, with rm or ungate. The guard blocks the loop's known removal paths.Supervised runs, throwaway branches, repos whose branch protection already gates merges.
Hard (opt-in)A root-owned marker outside the repo, plus a frozen .claude/. Only sudo unlock-loop.sh.Solo repos with no downstream review, unattended or overnight runs, direct-to-main.
 
$ sudo ./.claude/scripts/lock-loop.sh     # before /orchestrate
$ sudo ./.claude/scripts/unlock-loop.sh   # after you act on the card

While locked, "Allow always" on a permission prompt fails, because Claude Code writes that grant into the frozen .claude/. Choose "Allow once".
